## Design Specificity Verdict

**LLM assessment:** Nexus is visually authored for its product: exact SSH identities, terminal-native geometry, restrained violet/cyan semantics, and monochrome-safe reachability are distinctive and credible. The failure is hierarchy, not identity. The current wide layout behaves like a feature showcase around a launcher: navigation, three-line host rows, system metadata, tools, runbooks, topology, quick actions, fleet counts, legends, and footer hints all compete before the primary daily action.

The visual promise is a persistent remote workspace, but the lifecycle is a menu that disappears. The correct direction is host-first progressive disclosure: compact host list plus selected-host essentials by default; actions, tasks, saved commands, transfers, and fleet detail on demand.

**Deterministic scan:** The bundled detector returned exit 0 with `[]` for `dashboard.go`: zero rules, locations, or false positives. This is expected because its rules do not model terminal information hierarchy or Bubble Tea lifecycle behavior. PTY evidence caught what the static detector could not.

**Visual evidence:** Native terminal renders were inspected at 40×12, 80×24, and 120×32. Browser DOM overlays do not apply to a Bubble Tea TUI. At 120×32, selected-host identity and reachability repeat across header, legend, host row, detail view, and constellation. At 80×24, snapshot, tools, and runbooks are simultaneously visible. The palette contains operational actions but no definition or creation flow for saved commands.

## Overall Impression

Nexus already looks like a serious terminal product, but it spends attention proving breadth instead of accelerating the next action. The biggest opportunity is to turn it from a dashboard that launches commands into a calm host-first workspace that remains present while work progresses.

## What’s Working

- Exact `user@host[:port]` identities, frecency ordering, and latency make host choice trustworthy.
- Reachability uses glyph, text, and color together, so state survives monochrome terminals.
- Responsive layouts, cached host summaries, and the action palette are strong foundations for progressive disclosure.

## Priority Issues

### [P0] The TUI is not persistent during core work

**Why it matters:** `choose()` quits Bubble Tea and `runDashboard()` performs diagnostics, transfers, custom commands, and configuration afterward. Users lose selection, progress, failure context, and recovery precisely when the workspace matters.

**Fix:** Keep finite work such as metadata refresh and reachability inside Bubble Tea as asynchronous commands with per-host progress and success/failure messages. Restore the TUI after terminal-owning SSH, monitors, editors, and external transfer flows. Add a compact activity line and preserve selection across returns.

**Suggested command:** `$impeccable harden`

### [P1] The default wide composition spends attention on secondary features

**Why it matters:** Rail, status legend, three-column workspace, topology, quick actions, and footer duplicate information and make “choose host, connect” harder to see.

**Fix:** Default to two regions: compact two-line host list and selected-host essentials. Remove the permanent rail and bottom panels. Make fleet an optional overlay, actions a single palette, and secondary system detail progressively disclosed.

**Suggested command:** `$impeccable distill`

### [P1] Background status is fleet-wide and coarse

**Why it matters:** Probe results arrive as one batch, so fast hosts remain visually unresolved behind slow or offline hosts. Replacing known state with global “checking” reduces confidence.

**Fix:** Stream per-host results, retain last known status while refreshing, show `probing 7/24`, and support selected-host refresh without moving the current selection.

**Suggested command:** `$impeccable harden`

### [P1] “Runbooks” are unexplained and raw YAML is an activation dead end

**Why it matters:** `none configured · press e to add` neither defines a runbook nor shows its shape. Opening the entire config makes first-time users reverse-engineer YAML.

**Fix:** Label the concept `Saved commands` with a one-line definition and safe example. Add an in-TUI guide explaining name, description, exact command, scope, confirmation, and the YAML location. Keep `Edit full config` as the advanced path, not the explanation.

**Suggested command:** `$impeccable onboard`

### [P2] Too many overlapping interaction systems

**Why it matters:** Rail focus, details focus, direct mnemonic keys, palette, quick actions, and persistent footer hints compete. `Enter` can change meaning depending on invisible focus state.

**Fix:** Keep host navigation plus one action palette. Make Enter consistently connect, keep details non-focusable, show four contextual footer actions, and move advanced shortcuts into help.

**Suggested command:** `$impeccable clarify`

## Cognitive Load

The current wide view fails six of eight cognitive-load checks: single focus, visual hierarchy, one thing at a time, minimal choices, working-memory demand, and progressive disclosure. A returning user must parse ten simultaneous groups before acting. Reachability and action guidance each repeat across multiple regions. The target default should contain one decision—select a host—with no more than four persistent actions.

## Emotional Journey

- First launch: impressive, then uncertain about where to begin.
- Host selection: confidence improves because identity, port, latency, and recency are clear.
- Exploration: confidence falls as secondary regions compete.
- Action: continuity breaks when Nexus disappears.
- Failure or waiting: the user is returned to a shell without anchored explanation.
- Desired daily loop: open, recognize, act, observe, and return to the same selection.

## Persona Red Flags

**Jordan, first-time user:** Sees Hosts, Fleet map, Actions, Refresh, Themes, snapshot, tools, and Runbooks before understanding the primary path. “Runbook” is undefined and adding one unexpectedly opens YAML.

**Alex, keyboard power user:** Search and shortcuts are fast, but overlapping bindings and focus-dependent Enter add friction. Diagnostics and transfers destroy the workspace instead of becoming observable tasks.

**Sam, keyboard/accessibility-dependent user:** Glyphs have text equivalents and keyboard coverage is strong, but asynchronous state is not announced incrementally and focus can move to non-interactive details. Dense multi-region layouts increase cognitive-navigation cost.

**Incident-mode operator:** Repeated status signals make the selected host and current failure harder to isolate. Leaving the TUI during a failed diagnostic removes the operational context needed to recover.

**Many-host operator:** Batch completion makes the fleet appear stuck; three-line rows sharply reduce scan density; offline hosts dominate without contextual filtering.

## Minor Observations

- “Remote workspace” is the right positioning once lifecycle persistence is real.
- “Fleet constellation” is memorable but visually expensive; “Fleet” is sufficient.
- Cached data should distinguish fresh, stale, refreshing, and unavailable.
- The permanent status legend belongs in help.
- The empty-host state should eventually support guided creation inside the TUI.

## Questions to Consider

- If most launches end in SSH, what information must exist before choosing a host?
- Can Nexus call itself a workspace if finite operations close it?
- What would the footer feel like as a living task timeline instead of a repeated shortcut legend?
- Is fleet topology helping an operational decision, or mainly demonstrating rendering capability?
